Read this first

Observed workspace: one Teck.Cloud workspace; repository links for Teck.Cloud, Teck.Coolify, Teck.AiTools, Teck.GitOps, and Teck.Terraform; online runtime Oh-My-Pi (teck-multica-omp-1); two existing agents named Orchestrator and Deep Research Agent; shared MCP servers Firecrawl, Github, Github-Projects, and Searxng. There are no projects, custom workflows, or autopilots yet. Triage status exists, but its current description is truncated.

Two separate records, with a clear authority: GitHub Issues and native GitHub subissues hold the agreed scope, acceptance criteria, priority, dependencies, and final closure. Multica issues hold agent assignments, runs, handoffs, and local workflow state. Every active Multica delivery issue must link its canonical GitHub issue; a verified false-alarm intake can be Cancelled without creating one. Agents update GitHub through the assigned Github and Github-Projects MCP servers and verify the result by reading it back.

Multica does not synchronize GitHub Issues by itself. This setup relies on the agents following the instructions below; it is not a transactional sync service. Do not silently claim the two records agree when a GitHub MCP call fails.

Use the existing Oh-My-Pi runtime. Multica issues, workflows, and wakeups carry work between runs. No custom runtime profile is needed for this setup.

OMP helpers inside a Multica run: OMP's built-in task tool can spawn its bundled subagents in print/JSON mode. These helpers work inside the assigned Multica agent's run; they are not separate Multica agents or GitHub subissues. The Multica image does not install the shared Orca-specific custom subagent presets, because their instructions refer to Orca dispatch and skills.

In each Multica agent's Custom Args, add one token --wait-async. This keeps a headless run alive until its background task jobs deliver their results. On Lovelace, add a second token --advisor to enable OMP's advisor for that run. The image maps modelRoles.advisor to omniroute/teck-advisor and installs WATCHDOG.md and WATCHDOG.yml in OMP's user directory. The single enabled Implementation watchdog checks concrete drift every third turn. Its global advisor.enabled is false, so the argument is needed. OMP's advisor can steer a running turn in print/JSON mode, but final advice does not silently start another turn after the run settles. Hopper remains the independent Multica review step.

Three review passes inside the existing In Review step: Hopper asks OMP's bundled reviewer for correctness and regressions, bundled security-reviewer for reachable security issues, and the installed quality-reviewer for maintainability and test quality. Hopper and all three review passes use omniroute/teck-advisor. OMP's teck-judge role is for internal judgments, not the review agent. All passes inspect the same exact PR/base-head snapshot. Hopper deduplicates their findings, checks terminal CI and issue acceptance criteria, and posts one verdict. OMP's /review command works in headless mode, but its interactive mode menu is absent there; explicit task dispatch gives these three passes a stable target.

Subagents work in the Multica run's checkout. The current OMP setting has task.isolation.enabled: false; do not assign overlapping edits to parallel helpers. If a helper discovers a separately trackable deliverable, the parent agent updates the canonical GitHub issue and asks Columbo to create a native subissue when the split rule is met.

4 · GitHub Issues are the working backing store

This is the rule every agent and workflow step follows. A Multica issue is the execution counterpart of one canonical GitHub issue, with URLs in both directions. A GitHub parent can have native subissues when the deliverables are genuinely separate. Research, review, test runs, and OMP helper agents stay on the same issue unless they are independent deliverables.

GitHub owns

Outcome and acceptance criteria; primary repository; native subissue tree; blocked-by relationships; priority and Project fields; closure after verified delivery.

Multica owns

Named agent assignment; run transcripts; workflow step and handoff; local working checkout; evidence comments; wakeups when work waits.

Paste into a new canonical GitHub issue body

## Outcome
[One observable result.]

## Acceptance criteria
- [ ] [Behavior or artifact that can be checked.]
- [ ] [Relevant tests, integration check, or rollout evidence.]

## Scope
Primary repository: [Teck-Lab/repo]
Other repositories, if needed: [links]
Out of scope: [explicit exclusions, if any]

## Plan and dependencies
[One issue by default. Add native subissues only for separate deliverables.]
[Record real blocked-by relationships; parentage does not mean dependency.]

## Verification and closure gate
[Exact CI result, AI review verdict, any required human decision, rollout/apply, and observed post-change check.]

## Multica execution
[Multica issue identifier and URL once created.]
  1. Intake: Columbo searches the primary repository's GitHub issues via MCP; reuse an existing one for the same outcome. Then create or link the matching Multica issue.
  2. Planning: Columbo keeps acceptance criteria and dependencies on GitHub. When creating a native subissue or blocker edge, read it back before releasing dependent work.
  3. Execution: Lovelace comments material progress, failures, and PR links on GitHub, and posts the same run evidence to Multica. Branch or PR title includes the Multica identifier so its PR card links automatically.
  4. Review and delivery: Hopper records the AI verdict and routes approved work to Delivery. When human action is needed, the agent moves the Multica issue to Blocked with the exact question, which assigns the project lead. A merged PR does not close the GitHub issue when rollout verification is still outstanding.
  5. Close: after direct verification, Columbo or the authorized owner closes the GitHub issue via MCP, reads it back, records the evidence on the Multica issue, then moves Multica to Done.

Subissue split rule from Orca: split only when there are distinct deliverables with independent acceptance criteria and a concrete benefit from separate ownership, parallel execution, staging, or blockers. A second agent or checkout alone is not a reason to create a GitHub subissue.

When done, move to and If rejected, send back to tell an agent which status to choose; neither moves an issue automatically when a run ends. There is no “At start” field. Todo sends intake to Triage; Triage has its own Columbo handoff so an In Progress rejection actually returns to the triage agent. All later agent steps have a normal rejection destination. The agent can move directly to another relevant status when its evidence identifies a different owner or failed gate.

How agents handle trouble: Fix a local problem in the same step and record the attempt; for a pending external event such as CI, keep the same step and set a bounded wakeup. Reject unacceptable input to the configured earlier step with exact findings and a specific next action; its handoff starts the responsible agent. Ask Curie or OMP's advisor for a bounded investigation when the agent lacks evidence. Move to Blocked only for an outside dependency or a decision that requires you; the Blocked handoff assigns the project lead. A rejection never means automatically assigning you. If the same fix fails again without new evidence, stop repeating it and choose investigation, an earlier step, or Blocked based on the cause. Update the canonical GitHub issue with each material status change.

Wait for PR CI without a new workflow status

OMP's --wait-async waits for OMP subagents, not GitHub Actions. Lovelace waits in In Progress; Hopper waits in In Review. The PR must be linked directly to the Multica issue. After checking current required checks, the agent can create this wakeup while checks are still pending:

multica issue wakeup create <MULTICA_ISSUE_ID> --until-pr checks --expires-in 72h --on-timeout wake --instruction "Recheck required CI on the directly linked PR at its current head. Record exact conclusions. Continue the current workflow step only if its gate passes; fix or send back a failure, and investigate a timeout."

Multica's CI wakeup only catches checks that finish after the rule was created. Recheck the PR immediately after creating the rule; if checks have already reached a terminal state, disable the now-unneeded wakeup and handle that result in the current run. The deadline wakes the same agent for investigation if no CI event arrives. A wakeup created by an agent inherits that run's workflow step.

The Multica GitHub App webhook is for PR/CI display; it is not the autopilot webhook. In each repository, a GitHub Actions workflow can send only failed completed runs to the autopilot URL. Save that URL as MULTICA_FAILURE_WEBHOOK_URL in Actions secrets, then use a stable idempotency key based on run ID and attempt. The following is a template; replace CI with that repository's actual workflow name:

name: Notify Multica of failed CI
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
jobs:
  notify:
    if: github.event.workflow_run.conclusion == 'failure'
    runs-on: ubuntu-latest
    steps:
      - name: Send failed run
        env:
          URL: ${{ secrets.MULTICA_FAILURE_WEBHOOK_URL }}
          REPOSITORY: ${{ github.repository }}
          RUN_ID: ${{ github.event.workflow_run.id }}
          RUN_ATTEMPT: ${{ github.event.workflow_run.run_attempt }}
          RUN_URL: ${{ github.event.workflow_run.html_url }}
          HEAD_SHA: ${{ github.event.workflow_run.head_sha }}
        run: |
          test -n "$URL"
          jq -n --arg repository "$REPOSITORY" --arg run_id "$RUN_ID" \
            --arg run_attempt "$RUN_ATTEMPT" --arg run_url "$RUN_URL" \
            --arg head_sha "$HEAD_SHA" \
            '{event:"ci.failed", repository:$repository, run_id:$run_id,
              run_attempt:$run_attempt, run_url:$run_url, head_sha:$head_sha}' |
            curl --fail-with-body --retry 2 -X POST "$URL" \
              -H "Content-Type: application/json" \
              -H "Idempotency-Key: $REPOSITORY-$RUN_ID-$RUN_ATTEMPT" \
              --data-binary @-

In the HTML-rendered copy, the ${{ ... }} expressions are literal GitHub Actions expressions. Review each repository's existing workflow names and security policy before adding the relay.
