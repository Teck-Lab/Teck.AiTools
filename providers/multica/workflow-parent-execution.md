Parent and child execution rules

Approval covers the child briefs, stages and dependencies in the approved parent plan. A listed child inherits that approval and can start when its dependencies are verified. Keep later stages in Backlog until they are ready. Send materially changed scope, new children, or changed dependencies back through the parent workflow's review and approval gates before starting the affected work.

On a parent run, check current child statuses, dependencies, and queued or active runs. Start every ready child in the earliest eligible stage through its implementation handoff. Repair missing handoffs with one dispatch after verifying no equivalent run is queued or active. Verify each required child's delivery before advancing a dependent stage. Cancelled counts as closed for stage wakeups and requires an explicit scope decision before it can satisfy a deliverable.

If a child needs an answer or outside action, put the exact question or dependency, the person or issue that can resolve it, and the previous workflow step on the child. Register a wakeup for the owner who can resume that step before moving the child to Blocked. Use a comment wakeup filtered to the expected member when known, or an issue-status wakeup for an identified dependency. On wake, verify that the answer or dependency actually resolves the block. Restore the previous workflow step and its owner when the approved scope still applies. Route a material change back through the parent plan gates. Keep the parent In Progress while any independent work is runnable or active. If all remaining work is blocked, record links to the blocking children and a resumption condition, and move the parent to Blocked. Wake the parent coordinator when the blocker clears, even if the Blocked step hands the issue to a human.

Before ending an unfinished parent run, use the native stage completion wakeup and, when needed, a targeted child wakeup for a blocked issue or a review handoff without an owner. While the parent is In Progress, keep one pending recovery timer if there is no equivalent check. Re-read the parent, child statuses and runs when it fires, repair missed handoffs, and renew only while needed. Close obsolete wakeups as work advances. An In Progress parent must have a queued or active handoff, or a named wait with an enabled wakeup.

Before moving the parent to In Review, summarize what each child actually delivered in the parent Multica issue, link its evidence, and explain how the results meet the parent acceptance criteria together. Use the linked child issues for progress. Coordinate the parent without creating a duplicate implementation checkout or PR.
